# react-bench: specialize React SSR for a known app with unknown data

A shared benchmark for React SSR specializers. The app is fixed and known ahead of time; the
request data is not. Implementations under test:

1. Prepack's revived React compiler (symbolic partial evaluation, `src/react/`).
2. The "hybrid": runs the code in V8, then does trace-based specialization with guards and a fallback.
3. Reference points in this folder: `impl/baseline.js` (plain `ReactDOMServer.renderToString`) and
   `impl/handwritten.js` (the whole page specialized by hand into string concatenation, which
   gives an upper bound).

Everything is plain CommonJS on Node. React 18.3.1 and react-dom 18.3.1 are resolved from
`react-bench/node_modules`, then `bench/node_modules`, then `/tmp/opencode/pp-wt/bench/bench/node_modules`
(`react-deps.js`). The root `node_modules` has React 16 for Prepack's own tests, and this harness never uses it.
`NODE_ENV` defaults to `production`.

## Quick start

```
node react-bench/check.js --impl baseline                 # 500/500 byte-identical
node react-bench/check.js --impl handwritten              # 500/500 byte-identical
node react-bench/check.js --impl /abs/path/to/my-impl.js  # your implementation
node react-bench/perf.js  --impl /abs/path/to/my-impl.js  # throughput (JIT + --jitless) and cold start vs baseline
```

From another worktree, run the harness straight from this one, e.g.
`node /tmp/opencode/pp-wt/react-bench/react-bench/check.js --impl $PWD/react-bench/impl/prepack.js`,
or merge the `react-bench` branch.

## The app (`app/app.jsx` → `app/app.js`)

"Northstar Supply" is an industrial-tools e-commerce catalog page: a product listing with a
deal-of-the-day spotlight, a filter sidebar, a cart/quote summary, header, nav and footer.
It has 30 function components plus `App`, and is 944 lines / 31 KB once compiled.
`app/app.jsx` is the source. `app/app.js` is generated by `node react-bench/build-app.js`
(Babel classic JSX runtime with `useBuiltIns`, so spreads become `Object.assign`) and is committed.
**Implementations get `app/app.js`.**

Tree (depth in brackets): `App`[1] → 3 context providers → `PageShell`[2] →
`AnnouncementBanner`, `SiteHeader`[3] → `SearchBox`/`UserMenu`/`PrimaryNav`[4] → `NavItem`, `AvatarBadge`, `LoyaltyBadge`[5] → `CountPill`[6];
`Breadcrumbs`; `FilterSidebar`[3] → `FilterGroup`[4] → `FilterOption`[5] → `CountPill`[6];
`HeroSpotlight`, `CatalogToolbar`, `ProductGrid`[4] → `ProductCard`/`EmptyCatalogState`[5] →
`ProductBadges`, `StarRating`, `SpecList`, `PriceBlock`, `StockBadge`, `ActionButton`, `ReviewSnippet`[6];
`PaginationBar`; `CartSummaryAside`[3] → `CartLineItem`[4]; `SiteFooter`.

Features covered:

| Feature | Where |
|---|---|
| `.map` lists with keys, of varying length including empty | categories, crumbs, filter groups and options, products (0 to 210), specs, cart items, pages |
| Keyed `React.Fragment` in a list; `<>` fragments | `Breadcrumbs`, `SpecList`; `UserMenu`, `PriceBlock`, `CartSummaryAside`, `SiteFooter` |
| Conditional rendering | sale, clearance and featured badges; out-of-stock / low / in-stock; signed in vs anonymous; empty catalog state; optional promo, spotlight, review and specs; components returning `null` |
| Context (theme, locale, user) via `useContext` | `ThemeContext`, `LocaleContext`, `UserContext` |
| `useMemo` | `App` (stats loop), `CartSummaryAside` (totals loop) |
| `useId`: deterministic, position-dependent ids, also inside lists | `SearchBox`, `FilterSidebar` (two ids, giving `:RcH1:`), `CatalogToolbar`, and `FilterOption` inside nested `.map`s (`:R3fc:`, `:R5fc:`, ...) |
| Props spreading (`{...obj}`) | `ActionButton` (spread then override), `ProductCard` (spread `data-*` attributes) |
| `className` composition (`cx` with `Object.keys` loop) | everywhere |
| Inline style objects (px units, unitless numbers, `undefined` entries) | `PageShell`, `AvatarBadge`, `StarRating`, `ProductCard` (`order`, conditional `borderColor`) |
| HTML escaping of user text with `<>&"'` in text **and** attributes | product titles (also in `title` / `aria-label`), reviews, user names, search query (`value=`), labels |
| Number formatting (hand-written; no `Intl`) | `formatMoney` (`toFixed`, grouping, locale separators, 0-decimal JPY, negatives), `formatInt`, `toFixed(1)` |
| Date formatting (pure integer UTC civil-from-days; no `Date`, no TZ) | review dates, ship dates, deal end, footer timestamp (including epoch 0 and negative) |
| `dangerouslySetInnerHTML` (once) | `AnnouncementBanner` |
| Boolean attributes | `hidden`, `disabled`, `readOnly`, `required`, `open`, `itemScope`, `checked` (`defaultChecked`), `selected` (`<select defaultValue>`) |
| `data-*` / `aria-*` with string, number and boolean values | everywhere |
| Adjacent text children (React emits `<!-- -->` separators) | `"Only ", n, " left"` and many more |
| Loops / regex / string methods inside render | `formatDateUTC`, `groupDigits`, `computeInitials` (`split(/\s+/)`), `PaginationBar` (`for` loop + `push`) |

The page variants come from the same app and differ only in data:

| | elements per page (min / median / max) | HTML size | renderToString (JIT) |
|---|---|---|---|
| small | 47 / 106 / 161 (0 to 2 products) | ~6 KB | ~0.07–0.1 ms |
| large | 4,107 / 4,555 / 5,062 (170 to 210 products) | ~285 KB | ~5–7 ms |

## Data (`data.js`)

The request generator is seeded and deterministic (Mulberry32; no `Math.random`, `Date.now` or `Intl`).
Each request has theme, locale (`en-US`, `en-GB`, `de-DE`, `fr-FR` with a space as group separator,
`ja-JP` with 0 decimals), user or `null`, promo or `null`, search state, categories, breadcrumbs,
filters, spotlight or `null`, products and cart. Edge cases appear both randomly and in 4
hand-written inputs at the head of the corpus:

- empty lists everywhere;
- missing optional fields (`undefined` and absent), `null` objects;
- prices of 0, negative rebates and credits, negative loyalty points;
- epoch 0 and pre-1970 dates;
- XSS-looking strings in text and attributes;
- CJK, Arabic (RTL) and emoji text. A user name ending in an emoji even yields a lone surrogate
  through the app's `slice(0, 1)`, which is a realistic bug the output must reproduce exactly.

Corpora:

- `getCheckCorpus()`: **the fixed 500-input correctness corpus**. It has 4 edge cases, 471 small pages
  and 25 large pages. Fingerprint `4fafe7d601e3561d` (printed by `check.js` and `node react-bench/data.js`).
- `getSmallCorpus()` (500 inputs) and `getLargeCorpus(100)`: the throughput corpora. `perf.js` cycles
  through them, so every iteration gets different data.
- `getTrainingCorpus(n, variant)`: disjoint seeds, for implementations that trace or profile.
  It is exposed as `opts.trainingInputs`. **Do not train on the check corpus.**
- `node react-bench/data.js --dump corpus.json` writes the check corpus as JSON. JSON drops
  `undefined`-valued keys, and the app treats those the same as absent keys.

## Implementation interface

```js
module.exports = {
  name: "my-impl",
  prepare(appSource, opts) {          // called once per process; compilation happens here
    const render = data => "<div id=\"northstar-app\" ...";   // === renderToString(<App data={data}/>)
    render.code = generatedProgramText;  // optional but please set: used for the code-size report
    return render;                       // or { render, code, stats }
  },
};
```

- `appSource` is the text of `app/app.js`. It is a CommonJS module that does `require("react")` and
  `module.exports = App`. The root element is always `React.createElement(App, { data })`.
- `opts`:
  - `appPath`, `jsxPath`, `reactBenchDir`, `rootProp: "data"`;
  - `generateSampleInput(seed, "small"|"large")`, `trainingInputs(n, variant)`;
  - lazily loaded (React is only loaded if you touch them): `React`, `ReactDOMServer`, `require`
    (resolves `react` 18), `reactNodeModules`.
- `render(data)` must return a string that is **byte-identical** to `renderToString`. That includes
  `<!-- -->` text separators, attribute order, `useId` values, style serialization and escaping.
  It must not mutate `data`, and must not depend on call order or earlier inputs (falling back
  to React is fine). `check.js` passes each call a fresh deep copy. `perf.js` passes corpus objects
  directly, cycling.
- Code size: `check.js` measures `result.code`, `result.generatedCode`, `render.code` or
  `render.generatedCode`, otherwise `render.toString()`. Report all generated code that runs at
  render time, including helpers. Leave out unmodified React if you fall back to it, but say so in `stats`.
- Cold start: `perf.js` runs a fresh process per measurement and **discards the first run**.
  So an implementation whose `prepare` is expensive (e.g. running Prepack) may cache its output
  on disk, keyed by a hash of `appSource`. The steady-state cold start then measures loading the
  artifact. `prepare` time is reported separately either way.

## `check.js` (correctness)

```
node react-bench/check.js --impl <module> [--only small|large] [--limit N] [--all-mismatches] [--json out.json] [--quiet]
```

This renders every corpus input with both the reference (`require("app/app.js")` +
`renderToString`, loaded independently of the implementation) and the implementation. On a
mismatch it prints the first one with offset, differing characters and context. It also prints
the pass count, throws versus mismatches, `prepare()` time, generated code size (bytes, gzip,
lines) next to the size of `app.js`, and the corpus fingerprint. It exits with 1 on any failure.

## `perf.js` (throughput and cold start)

```
node react-bench/perf.js --impl <module> [--impl <module2>] [--variants small,large] [--engines jit,jitless]
                         [--time 3] [--warmup 1.5] [--rounds 3] [--cold-runs 7] [--no-cold] [--quick] [--out file.json]
```

`baseline` is always included. The run starts with a sanity check (22 inputs must match the
reference), then:

- **Throughput**: one fresh child process per cell (impl × page × engine × round), so neither JIT
  state nor inline caches leak between implementations. Each child calls `prepare`, warms up for
  `--warmup` s (and at least one pass over the corpus), then renders for `--time` s, cycling
  through the corpus. It reports renders/s, mean, p50, p90 and p99 ms per render, and **allocated
  bytes per render** (the delta of V8's `total_allocated_bytes`, garbage included). Rounds are
  interleaved, and the reported numbers are medians over rounds. "speedup" is the median of the
  per-round impl/baseline ratios, which is robust to background load on a shared machine.
- **Engines**: `jit` is plain node. `jitless` is `node --jitless`: V8's interpreter only (Ignition),
  which approximates no-JIT environments such as iOS JavaScriptCore without JIT, or locked-down
  embedders.
- **Cold**: fresh processes under each engine. Each one loads the impl module (including React,
  if the impl needs it), runs `prepare`, then renders 2 small inputs. Reported per phase: load,
  prepare, first render, second render, and "first HTML" (load + prepare + first render). These
  are medians of `--cold-runs` runs, after one discarded priming run.

The output is a markdown table on stdout. JSON and markdown go to
`results/perf-<impls>.json` and `.md` (or `--out`).

## Results

See `results/README.md`. Headline numbers (baseline → handwritten, on a noisy shared 4-vCPU box):

| | JIT small | JIT large | jitless small | jitless large | cold first HTML (JIT) |
|---|---:|---:|---:|---:|---:|
| baseline | 0.157 ms | 6.1 ms | 1.02 ms | 58 ms | 32 ms |
| handwritten | 0.020 ms | 1.2 ms | 0.071 ms | 3.1 ms | 1.9 ms |
| speedup | 9.0x | 5.6x | 15x | 18x | 17x |
